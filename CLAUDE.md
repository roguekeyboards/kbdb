# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

See [`README.md`](README.md) for what this project is and its architecture decisions, and [`CONTRIBUTING.md`](CONTRIBUTING.md) for commands, AWS account/deploy setup, and testing strategy — both are the authoritative human-facing docs; this file only adds guidance specific to working as an AI coding agent here.

## Working in this repo

The project is being built issue-by-issue against a fixed architecture (see `README.md`); GitHub issues in this repo are the authoritative source of what's scoped/in-progress/deferred. Check open issues before assuming something is unimplemented or undecided.

**Run `mise tasks` (or read `mise.toml`) before reaching for a raw `go`/`docker`/`sam` command.** This repo has task aliases for the operations agents redo constantly — `mise run lint`/`l` (lint Go + workflows), `mise run test`/`t` (unit tests only, excludes `test/functional`), `mise run build`/`b` (`sam build`), `mise run gen`/`g` (regenerate mocks + OpenAPI types + the HTTP API's routes + `go mod tidy`) and `check-generated`/`cg` (run `gen` and fail if anything changed — what CI enforces), `mise run migrate-build`/`mb` (build the `kbdb-migrate` CLI; not covered by `sam build`), `mise run func-setup`/`fs` (deploy `template.yaml` to [floci](https://github.com/floci-io/floci) via a real `sam deploy`, plus generate local OIDC signing material via [`oidc-testkit`](https://github.com/rogueserenity/oidc-testkit)) and `func-test`/`fx` (run the Ginkgo functional suite against it) + `func-teardown`/`ft`, and `setup`/`deploy`/`teardown [env]` for an AWS environment defined in `samconfig.toml` (defaults to `dev-$(whoami)`). Don't invent an equivalent by hand (e.g. `go build ./... && go test ./...`) — it'll do the wrong thing (`go test ./...` alone hangs/fails on functional tests with no live infra) and skip whatever the script actually does around it.

## Architecture notes for agents

**`internal/auth`'s verification logic is protocol-agnostic.** `Verifier`/`VerifyToken` take and return a raw token string and claims; they know nothing about HTTP, Lambda, or MCP. This is what lets the same verifier be reused by both the REST middleware (`internal/middleware.Auth`) and the MCP server without duplicating verification logic per protocol. The one sanctioned exception is `auth.BearerToken` (`internal/auth/http.go`), which does import `net/http` — pulling a bearer token out of an `Authorization` header is HTTP-shaped regardless of which protocol rides on top, so both transports share it rather than each writing their own. Don't add further `net/http` dependencies to this package.

**`internal/auth.Verifier` depends on an unexported `tokenVerifier` interface, not the concrete `*oidc.IDTokenVerifier` type**, specifically so unit tests can inject a mock (`internal/auth/mocks`, generated by `mockery` — see `.mockery.yml`) instead of standing up a real OIDC discovery round-trip or hand-signing JWTs. This is deliberate: correctness of `go-oidc`'s own signature/expiry/issuer/audience validation is not this project's concern to unit-test (that's testing a well-tested third-party library, not our code) — those tests were removed in favor of ones that verify *our* wiring calls the verifier and propagates its result correctly. Real end-to-end rejection-path coverage (expired tokens, bad signatures, etc., actually being rejected) belongs at the functional/black-box test layer, against the [`oidc-testkit`](https://github.com/rogueserenity/oidc-testkit)-signed tokens the functional suite mints, not here.

**Dependency injection over hand-written mocks is the codebase-wide default, not an auth-specific trick.** When code needs a collaborator that would otherwise drag in a live AWS/network dependency, define a narrow interface covering only the methods actually used, inject it, and generate a `mockery` mock for tests. `internal/repository/dynamo`'s `dynamoAPI` and `internal/repository/s3`'s `s3API`/`s3PresignAPI` follow the same shape.

**Generated mocks live in a `mocks/` subpackage next to the code they mock (`auth/mocks/`, `repository/mocks/`, `repository/dynamo/mocks/`, `repository/s3/mocks/`), never alongside the source file.** Add new interfaces to mock under `.mockery.yml`'s `packages` entry rather than hand-writing a mock; give the generated struct an exported name (e.g. `structname: 'MockTokenVerifier'`) since an unexported interface still needs an importable mock type from the separate `mocks` package. Regenerate with `mise run gen`, not a bare `mockery` — `gen` also reruns `oapi-codegen` and `go mod tidy`, and `check-generated` (which CI runs) fails if any of the three would change something.

**Package layout under `internal/`**. Most of these packages carry a `doc.go` explaining their boundary and why it exists — read it before assuming a package's scope.

Identity and request plumbing:
- `auth/` — authentication: verifying a token, establishing who the caller is (`Verifier`, `VerifyToken`, `Claims`, `BearerToken`). Does not decide what the caller may do.
- `authz/` — authorization: what an already-identified caller may read or write. Does not verify tokens.
- `ctx/` — request-scoped identity values on `context.Context`. Independent of logging and of any transport; business logic needing the caller's user ID depends on this directly.
- `log/` — request-scoped `*slog.Logger`-in-context plumbing. Knows nothing about where field values come from; callers pass them in.
- `ownerprefs/` — the item owner's profile preferences on a REST request's context, put there by `middleware.OwnerPreferences` from the `{userId}` path segment. MCP tools call `GetPreferences` directly.

Transports (each maps to shared logic rather than holding its own):
- `middleware/` — `net/http` middleware: `Auth`, `Logging`, `Recover`, authorizer context, and `OwnerPreferences`, which every `{userId}` route whose handler returns a price must be wrapped in (`ownerPrefs(...)` in `router.go`).
- `handlers/` — REST route handlers, one file per entity. Kept separate from middleware and router wiring.
- `handlers/api/` — `api.gen.go`, generated from `api/openapi.yaml` by `oapi-codegen`; do not hand-edit (see `mise run gen`).
- `router/` — wires handlers + middleware into the application's `http.Handler`. No logic of its own.
- `gatewayroutes/` — generates `api/gateway.gen.yaml`, the API Gateway routes `template.yaml` includes, from `api/openapi.yaml` (each operation's `security` decides whether the gateway's JWT authorizer applies). A new REST route needs only the spec and `router.go`, then `mise run gen`; a route outside the spec goes in `extraRoutes`. Never add SAM `HttpApi` events: each adds a resource-policy statement, and ApiFunction's policy hit Lambda's 20 KB limit.
- `mcp/` — MCP server over the official `modelcontextprotocol/go-sdk`, reusing the same `auth.Verifier` as REST. `mcp/schema/` holds the tool types.
- `consent/` — the IdP consent page served at `GET /authorize`, which also handles OIDC logout requests, so MCP clients can authenticate standalone.
- `legal/` — the privacy policy and terms of service at `GET /privacy` and `GET /terms`. Served here, not by mykeebs-web, because they cover MCP and REST too. The privacy policy names the processors and retention periods in `template.yaml`; change it when those change.
- `pagebrand/` — the logo, favicon and theme tokens that `consent/` and `legal/` pages embed inline.
- `problem/` — RFC 9457 Problem Details responses.

Data access:
- `repository/` — per entity, the data-model struct and the interface of operations on it. No AWS SDK types.
- `repository/dynamo/`, `repository/s3/` — the concrete implementations.
- `repoapi/` — maps `repository`'s DB-shaped types to `handlers/api`'s generated spec-shaped types, once per entity instead of inline in each handler.
- `repomcp/` — the same mapping role for `mcp/schema`'s tool types.

Shared business rules (deliberately transport-neutral, called by both REST and MCP so the rules can't drift):
- `lookup/` — validates entity fields against approved lookup category values.
- `buildrefs/` — validates a Build's cross-entity references against live repository data.
- `cascadedelete/` — the block/cascade/detach `on_delete` policy for items still referenced by Builds.
- `accountdelete/` — deletes a whole account (images by key prefix, items by `user_id` partition, then the profile), behind the REST profile delete and MCP `delete_profile`.
- `profileread/` — resolves a profile identifier and applies the discoverable-or-owner visibility rule.
- `profilevalidate/` — field-level rules for a profile's writable body.

Image moderation:
- `imagekey/` — parses an image's object key back into the entity, owner and IDs it belongs to.
- `moderation/` — the moderation function's logic (`functions/moderate` only wires it to Lambda): read the image's status first, ask Rekognition, write approved/rejected. `moderation.Images` routes a key to its repository's status read/write, for the operator CLI too; `Overrides` and `Rejections` are the CLI's approve/reject and log-query logic.

Follow this same split when adding an entity: a handler per route in `handlers/` and a tool in `mcp/`, both thin; the repository interface in `repository/` with its implementation in `repository/dynamo/`; mapping in `repoapi/`/`repomcp/`; and any rule both transports enforce in its own shared package rather than duplicated on each side or inlined in `router.go`.

**Lambda entrypoints live in `functions/`, standalone CLIs in `cmd/`.** `functions/api/` deliberately does not follow the `golang-standards/project-layout` convention of `cmd/<binary-name>/` — this was raised and considered explicitly, and `functions/api/` was kept because it more directly signals "this is a Lambda function" in this AWS-specific codebase. Don't "fix" this to `cmd/api/`; it's an intentional, discussed deviation, not an oversight. `cmd/` is not unused, though — `cmd/kbdb-migrate/` (the dump/restore CLI, built via `mise run migrate-build`) and `cmd/kbdb-moderation/` (the moderation operator CLI behind the `moderation-*` tasks; [`docs/moderation.md`](docs/moderation.md) is its operator guide, keep it in step with the CLI) are real binaries and belong there. `internal/` and `test/` follow the convention.

**`brand/` is mykeebs' logo, icons and design tokens, not kbdb code.** `tokens.json` and the designs in `brand/internal/art` are the source; `brand/dist/` is generated by `mise run gen` (via `brand/gen`) and never hand-edited. Go pages that need the logo or theme colours import `github.com/rogueserenity/kbdb/brand` (`brand.Files`, `brand.Tokens`) instead of pasting hex values or SVG; the same files are published to npm for mykeebs-web. Its images are compared within a pixel tolerance by `brand/internal/assets`' tests rather than by `check-generated` (rasterizing differs slightly across CPU architectures). See `brand/README.md`.

**Config is env-var-only, read via Kong (`functions/api/config.go`)**, not raw `os.Getenv` calls — Kong gives struct-tag-driven required-field validation and defaults even though there are no CLI flags to parse (this is a Lambda entrypoint, not a CLI tool). Add new config by adding a field to `Config`, not by reaching for `os.Getenv` elsewhere.

**`template.yaml` also declares an `AWS::Budgets::Budget`** (`CostBudget`) as a cost tripwire — don't remove it when touching the template, and raise the threshold deliberately if the project's real usage/cost profile changes rather than deleting it.

**Unit tests under `internal/` use `testify/suite`** (`type XSuite struct { suite.Suite }`, `TestXSuite` runner, `s.Equal`/`s.Require()` methods), not bare `func TestX(t *testing.T)` + `t.Run` tables. Applies even to small files. A `_test.go` file holding only shared helpers and no test cases of its own (e.g. `internal/mcp/tool_test.go`) needs no suite. `test/functional/` is Ginkgo instead — not covered by this rule.

**`test/functional/` specs follow strict Given/When/Then structure — every distinct precondition is its own nested `Context`, never a `BeforeEach` stuffed inside a `When`.** `Context` = Given (a precondition/state the system is in); `When` = the single action under test; `It`/`By` = Then (the assertion). The test-case-per-node rule: a `Context` may have exactly one `When` under it *unless* that `Context`'s precondition genuinely admits multiple distinct actions being exercised under it (e.g. a "given no bearer token" `Context` may exercise both the initialize handshake and a tool call, as two real, different actions taken under the same precondition — that's fine). If two `When`s under the same `Context` differ only in what request they send or what state exists beforehand (not in what's being verified as the action-under-test), that's a precondition difference misfiled as an action — split it into a nested `Context` per precondition, each with its own single `When`. Concretely: `Context("given the caller is X")` containing both `When("doing thing with valid input")` and `When("doing thing with invalid input")` is wrong — "valid input" vs "invalid input" is a `Given`, so it should be `Context("given the caller is X")` → two nested `Context`s (`"given valid input"` / `"given invalid input"`) → one `When` each. See `test/functional/features/api/profiles/profiles_get_test.go` (`"given the identifier is the owner's user id"` / `"given the identifier is the username"` as sibling `Context`s, each with one `When`) as the reference shape.
